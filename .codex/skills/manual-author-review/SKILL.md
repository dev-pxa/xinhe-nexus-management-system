# 操作手册编写与审查

## 目标

为当前项目生成可直接交付给新手使用的操作手册，并通过独立子 Agent 做事实审查和可操作性审查。手册必须以当前项目真实代码、真实路由、真实页面和真实交互为依据，禁止凭经验补写不存在的功能。

## 适用范围

- 用户要求编写、补充、重写或拆分项目操作手册。
- 用户要求给手册增加业务场景、操作步骤、截图、常见问题或角色说明。
- 用户要求验证手册是否与当前项目实现一致。

如果用户只要求修改普通项目文档而不涉及操作手册，不要自动套用本 Skill。

## 标准工作流

### 1. 先确定文档边界

1. 读取当前项目已有手册、目录大纲、`AGENTS.md` 和相关文档规范。
2. 确认用户要求的文件位置、一级标题拆分规则、是否需要保留已有内容。
3. 若已有大纲规定“每个一级标题为独立 md”，一个一级标题只能对应一个独立文档，不要把多个一级标题合并到同一文件。
4. 检查当前工作区状态，保留用户已有修改，不覆盖无关文件。

### 2. 以代码和页面为事实来源

写作前至少核对：

- 路由和菜单配置，确认实际菜单名称、层级、隐藏页面和访问条件。
- 页面代码，确认按钮名称、字段名称、表单校验、提交结果、状态和错误提示。
- 服务层接口，确认数据来源、状态流转、权限边界和成功/失败行为。
- 现有自动化测试，优先复用真实测试中的登录账号、页面入口和可验证断言。
- 如果项目提供可运行前端，使用当前项目端口实际打开页面，不能只依赖代码推测布局。

对于“管理员”“公司管理员”“平台管理员”“负责人”等角色，必须从访问控制和页面逻辑中核对，不要把角色名称混用。前端展示的枚举必须使用实际业务描述，手册也应使用业务描述，不直接写内部枚举值。

### 3. 编写手册内容

每个功能至少包含：

1. 功能用途：用新手能理解的语言说明解决什么问题。
2. 业务场景：说明什么角色、在什么情况下使用。
3. 进入路径：写出左侧菜单和页面标题的真实名称。
4. 操作步骤：按实际点击顺序描述，每一步使用页面上可见的文字。
5. 完成标志：告诉用户提交后应该看到什么状态或结果。
6. 常见问题：覆盖权限、数据范围、校验失败、状态不允许继续操作等情况。
7. 截图辅助：在关键操作附近插入真实截图，并说明截图中需要点击或观察的位置。

如果某模块当前待开发或代码中没有对应能力，明确写“待开发”，不要写成已经可用的操作流程。

### 4. 获取和管理截图

优先使用 Playwright 或项目已有 E2E 流程采集真实页面截图；无法自动化时再使用可用的浏览器 UI 工具。截图应：

- 保存在手册附近的稳定目录，例如 `docs/images/`。
- 使用有意义的英文文件名，避免把临时测试截图混入最终交付目录。
- 在 Markdown 中使用相对路径，保证文档移动到项目内仍能显示。
- 覆盖登录、导航、关键表单、提交结果、权限或状态等真正影响新手操作的画面。
- 每张截图配图注，说明页面区域、关键按钮和用户应观察的结果。

### 5. 独立审查 Agent

用户明确要求子 Agent 审查，因此必须使用 `multi_agent_v1__spawn_agent` 启动一个独立审查 Agent。审查 Agent 只负责检查，不直接替主 Agent 猜测或粉饰问题。向它提供：

- 当前手册文件路径。
- 相关项目源码、路由、测试和截图目录。
- “以当前代码和可运行页面为准”的审查要求。

审查 Agent 必须输出结构化结果：

```text
结论：通过 / 需修正
问题列表：
- 严重级别：P0/P1/P2
- 文档位置：文件、章节或步骤
- 事实依据：源码、路由、测试或页面证据
- 问题说明：具体哪里不一致、不完整或不可操作
- 修正建议：应改成什么
截图问题：缺失、过期、路径错误、说明与画面不符
```

审查至少覆盖 [references/review-checklist.md](references/review-checklist.md)。如果当前项目无法启动或无法访问页面，必须把该限制写入审查结论，不能把未验证内容判定为通过。

### 6. 独立修正 Agent

如果审查 Agent 返回任意需要修正的问题，必须再启动一个独立修正 Agent，让它根据“原始手册 + 审查报告 + 代码证据”修改手册和必要的截图，不要让审查 Agent 自己宣布修正完成。

修正 Agent 的要求：

- 只修改审查报告涉及的手册、截图或手册专用测试文件。
- 保留用户已有的无关改动。
- 修改后重新检查所有相对图片路径、标题层级、步骤编号和截图说明。
- 返回修改文件列表、修改摘要和无法修正的阻塞项。

### 7. 主 Agent 最终复核

修正完成后，主 Agent 必须重新读取修改后的手册，至少执行：

- Markdown 语法和相对图片路径检查。
- `git diff --check` 或同等空白检查。
- 对关键页面重新运行相关 E2E 或截图流程（如果项目可运行）。
- 抽查审查报告中的每个问题是否已经关闭。
- 检查手册没有残留 TODO、占位截图、内部枚举值、错误菜单名称或虚构功能。

如果修正后仍有问题，最多再进行两轮“审查 Agent → 修正 Agent → 主 Agent 复核”。达到三轮仍无法解决时，停止自动修改，明确列出阻塞原因并请求用户决定；不要无限循环。

### 8. 同步到飞书文档（强制）

每次新增或编辑操作手册，无论是主 Agent、修正 Agent 还是用户要求的小范围文字调整，都必须在本地内容完成后同步更新飞书文档；未完成飞书同步不得宣布任务完成。

默认知识库入口为：

`https://ncnpzim27ujc.feishu.cn/wiki/CGWswkJInix5nOkYUaXcX3oonHe?from=from_copylink`

同步规则：

1. 以本地 Markdown 为内容来源，先读取目标知识库目录下的子节点，按文档标题匹配已有章节；不要凭记忆创建重复文档。
2. 已存在的章节使用飞书文档更新操作覆盖或精确修改；本地新增的一级章节在同一目录下创建新文档。
3. 同步内容必须包含本地最新正文、标题层级、步骤、图注和截图。Markdown 中的本地图片引用要转换为飞书支持的本地资源引用，并确认图片实际上传成功；不能只同步文字而遗漏截图。
4. 总目录文档也必须同步：新增章节要加入索引，章节标题或链接变化要更新索引；没有结构变化时至少核验目录仍指向正确的章节文档。
5. 同步后重新读取飞书目录和受影响文档，核对标题、章节数量、关键文字、图片块和文档链接。若出现权限、认证、图片资源或更新失败，必须明确报告失败位置和原因，不能假设同步成功。
6. 若飞书认证已过期，按可用的 Lark/Feishu 文档技能完成用户授权后再继续；不得把未同步的本地文件当作最终交付。

建议记录每次同步结果：受影响的本地文件、对应飞书文档 URL、创建或更新动作、图片数量、校验结果和未解决问题。

## 交付要求

最终回复应包含：

- 已创建或更新的手册文件链接。
- 截图目录或新增截图列表。
- 审查 Agent 的结论和修正轮次。
- 自动化验证结果。
- 尚未解决的事实缺口或待开发内容。

除非用户明确要求，不要在本 Skill 中自动执行 Git commit，也不要因为生成手册而修改业务代码。
